# M0.5 Runtime & Deployment Stabilization

## Problem

Vercel detected the repository as Next.js, but the production script ran
`vinext build`. Vinext emitted `dist/` for the Cloudflare worker rather than
`.next/`, so Vercel failed after the build with `.next` not found.

## Root cause

The repository had two competing runtimes: Next.js application code and a
Vinext/Cloudflare Worker entrypoint. Routes also imported the Cloudflare-only
`cloudflare:workers` module directly.

## Architecture before

```text
vinext build → Cloudflare Worker → D1/R2/Workers AI
Next.js detection in Vercel → expects .next/
```

PostgreSQL was already the Drizzle adapter, but evidence uploads still called
the R2 binding directly and the AI route read the Workers AI binding.

## Architecture after

```text
next build → .next/ → Vercel
                         ├── Drizzle → PostgreSQL/Supabase
                         ├── Supabase Storage (private evidence bucket)
                         └── Supabase Auth foundation
```

The AI endpoint remains intentionally disabled with `503` when no provider is
configured. No new AI provider or educational functionality was added.

## Changes

- `dev`, `build`, and `start` now use native Next.js.
- Node is pinned to `22.x`.
- Removed the inactive Vinext/Cloudflare worker build path and its packages.
- Added `lib/storage/evidence-storage.ts` as the provider boundary.
- Evidence uploads use the private Supabase `evidence` bucket through a
  server-only service-role adapter. The service role is a temporary bridge
  until Storage policies can authorize user sessions directly.
- Removed runtime `cloudflare:workers`, D1, R2, and Workers AI imports.
- Added `MIGRATION_DATABASE_URL` for administrative migration workflows while
  `DATABASE_URL` remains the application runtime connection.
- Added a PostgreSQL privilege migration that grants authenticated users update
  access only to `profiles.display_name`.

## Security fixes

`profiles` remains protected by RLS. Column privileges now prevent an
authenticated client from issuing updates to `role`, `id`, or timestamps. The
existing database trigger also rejects role changes and normalizes
`updated_at`. The service role is referenced only from server-side storage and
development seed code; it is never a `NEXT_PUBLIC_*` variable.

## Deployment strategy

Vercel project `edu-signal` is the canonical deployment. The duplicate
`edu-signal-ct` project must be disconnected or removed manually in Vercel; it
cannot be solved safely in application code. Vercel should use the detected
Next.js framework and leave Output Directory empty. Required runtime variables
are `DATABASE_URL`, `NEXT_PUBLIC_SUPABASE_URL`, and
`NEXT_PUBLIC_SUPABASE_ANON_KEY`; the service key is required only for evidence
uploads while the temporary bridge remains.

## Migration strategy

`drizzle-postgres/` owns application schema migrations generated by Drizzle.
`supabase/migrations/` owns Supabase-specific Auth, RLS, Storage, and privilege
SQL. Bootstrap the schema with Drizzle first, then apply Supabase migrations
in filename order. Do not apply the historical SQLite files in `drizzle/` to
the PostgreSQL database.

## Remaining legacy dependencies

- `drizzle/` is historical SQLite/D1 migration history and is not runtime code.
- `educators`/`sessions` remain legacy identity tables for the already-started
  M1 transition and are not used by the runtime connection path.
- The Vercel deployment itself still requires verification in the canonical
  `edu-signal` project; the duplicate `edu-signal-ct` project is an external
  dashboard concern.
