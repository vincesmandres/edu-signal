# M6.1 Authorization Hardening

## Objetivo

Cerrar autorización server-side para credenciales, evaluaciones, rúbricas y evidencias sin cambiar proof crypto ni construir verify UI. La autorización no confía en `studentId` global: combina actor, classroom, recurso y enrollment activo.

## Findings

- Credential issuance aceptaba student global sin `classroomId` ni enrollment activo.
- Evaluation verificaba teacher/evidence, pero rubric y criterios requerían ownership y misma classroom explícitos.
- Rubrics filtraba lectura por teacher, pero creación aceptaba criterios vacíos/filtrados y escribía filas sin atomicidad.
- Draft evidence tenía prelectura con ownership, pero algunas escrituras finales filtraban sólo por id/estado.

## Archivos y decisiones

- `lib/authorization/index.ts`: helpers de classroom docente, evidence submitted, rubric owned, enrollment activo y evidence student-owned.
- `lib/authorization/policy.ts`: reglas puras de deny-by-default para pruebas offline.
- Credentials y rubrics usan transacción para filas de dominio y audit; conflictos únicos responden `409`.
- Rubrics exige lista no vacía, `maxScore` decimal positivo hasta 100 y nombres no duplicados.
- Student PATCH/DELETE/file/submit filtran escritura por `id + studentId + draft`; submitted permanece inmutable.
- PATCH/DELETE/submit/file incluyen además `EXISTS` correlacionado de enrollment activo en la escritura final. File upload usa `updatedAt` como versión esperada y nunca restaura metadata sobre una fila que cambió.
- Las cuatro mutaciones student-owned usan una transacción y el orden de locks fijo `enrollment FOR UPDATE -> evidence FOR UPDATE -> mutación CAS`; enrollment inactive/changed aborta con respuesta contextual.
- La creación de draft también usa `enrollment FOR UPDATE -> activity/module/classroom FOR UPDATE -> INSERT`; revalida contexto publicado y `requiresEvidence` dentro de la transacción. Conflicto único student/activity devuelve `409`.
- Cada upload usa `classroom/student/evidence/UUID/safe-filename`. Un CAS perdedor elimina sólo su propio objeto. DELETE hace commit DB primero y luego limpia la key exacta; PATCH file-to-text/link hace lo mismo. El cleanup verifica referencias antes de borrar, registra fallos sin path/PII y no revierte metadata.
- Credentials y evaluations revalidan contexto dentro de la transacción con `FOR UPDATE` antes de insertar; cualquier audit se escribe en la misma transacción.
- Las respuestas student/teacher usan DTOs que omiten `storageKey`; las URLs firmadas sólo se generan después de autorización.
- No se añadió migración: las invariantes nuevas son de autorización/validación y la unicidad de evaluación ya existe en M6.

## Adversarial tests

La suite offline cubre Teacher A/B, Student A/B, classroom/rubric cruzados, enrollment inactive, evidence ownership, condiciones de escritura final, orden de locks, paths únicos para uploads concurrentes, cleanup por objeto propio, redacción de DTOs, errores de payload y scores faltantes/extras/duplicados/fuera de rango. HTTP autenticado, Postgres transaccional real, carreras live, RLS y Storage privado quedan para M6.2.

## Riesgos

La rama no certifica side-channel behavior contra una base real ni RLS; el adapter usa conexión privilegiada y depende de estos guards. La URL firmada sigue siendo autorización temporal de descarga, no proof criptográfico.
